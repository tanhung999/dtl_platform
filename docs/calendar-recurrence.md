# Calendar recurrence

Events and scheduled notes support `NONE` (default), `DAILY`, and `WEEKLY`. Recurrence has no end date; weekly occurrences use the start date's weekday. A persisted event stores the first occurrence's start/end and one recurrence rule. Timed forms use one date and a start/end time; the end time must be later than the start time on that date. All-day events and notes retain an inclusive end-date field, stored as an exclusive next midnight. Saved date/time/all-day/recurrence controls are locked; edits are made and saved immediately through Reschedule. The weekly option names the weekday of the selected start date in Vietnam calendar dates, independent of the browser timezone. Existing multi-day entries remain unchanged until their schedule is edited.

The server projects occurrences into the requested range (maximum 93 days); each server page is capped at 500 items with accurate occurrence totals and explicit load-more controls. Counts in the mini calendar use the same projection. Occurrence IDs are opaque display IDs, while `series_id` identifies the persisted event used for detail/edit/delete. Shared views retain owner/scope/privacy checks before projection. Events and scheduled Notes offer three explicit scopes for deletion and Reschedule: `ALL`, `FOLLOWING`, and `THIS`. The UI names the selected occurrence date and defaults to `THIS`. `THIS` stores an exclusion and creates a non-repeating replacement for a move; scheduled Notes copy their content to that separately scheduled Note. `FOLLOWING` bounds the old segment with an exclusive `recurrence_until` timestamp and creates a new segment for a move, keeping earlier occurrences intact. Grid projection, totals, shared views, note previews and reminders respect the same cutoff/exclusions. The old per-occurrence edit/skip endpoints remain removed; scope is part of the existing delete/reschedule operations. Scoped moves keep request receipts, version guards, history and Undo; content drafts stay open. Whole-series moves update related segments and replacements together; whole-series deletion removes the linked family and pending reminders. A backup precedes the additive nullable-cutoff migration; no existing schedules are converted at startup.

Relative reminders repeat for each occurrence. Only the next pending reminder is queued; delivery schedules the following one transactionally, with a unique key per series version and scheduled timestamp. Offline delivery does not enqueue every missed occurrence. An absolute reminder is sent once at the chosen timestamp. Archive/delete/rule changes cancel or invalidate the pending reminder as appropriate. Rescheduling history and undo retain the recurrence rule.

Schema migration adds `calendar_events.recurrence` with default `NONE`; it does not convert or delete existing schedules. A database snapshot was saved in the ignored `.audit-backups` directory before the live migration.

Verification includes API recurrence/ownership/count limits, weekly notes, edit/stop/delete, stale writes, reminder delivery/deduplication/cancellation, reschedule/undo, and browser creation/editing/rendering/sharing tests.

The left sidebar keeps Create Event outside its scroll area. Only the mini calendar, filters and calendar list scroll. Mini-calendar markers have one fixed size and a separate row below each date number.

Notes scheduling starts with a selected day, 09:00–10:00 and no repeat. The explicit All Day checkbox hides time inputs and reveals an inclusive end date. After saving, dates, times, All Day and repeat are locked and changed through Reschedule. A repeating Note remains one Note and one linked appointment; it does not create one Note for each occurrence.

View preferences and scroll offsets are stored per account in tab-scoped sessionStorage. No API results or Note bodies are stored there, and reopening a view still reads the server.
